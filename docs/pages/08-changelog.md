# Changelog

What changed in each version of Origami. The launch screen shows the version you are running under the name; when a newer one is out, that line turns blue and underlined, and clicking it opens the download page.

## 0.1.0 (not yet released)

### Nov 23

- `origami frame` and `origami render` print the script's note, such as "line 3: lens 200 is lowered to 170, the most it takes", before they draw. Before, only `origami ir` and the app showed it. When a script has several such values the note is about the first one; before, it was about the last.
- A font name that is not installed, such as `text("Hi", { font: "NoSuchFontName" })`, now says it "is not a font installed on this Mac, or a font file next to the script". Before, it said the name "points to a file that does not exist", as if a file had been asked for.
- `curve` without its channel, as in `curve([[0, 0], [1, 1]])`, and `wheel` without its range now say which name goes first. Before, `curve` said it "takes points of two numbers", which the script had given, and `wheel` gave a JavaScript type error.
- A colour table (`.cube`) file that is empty, cut short or not a colour table at all, used with `look` or `inputLut`, now gives an error on its line as soon as the script is read. Before, the preview drew the clip without the look and said nothing, and only the export refused the file.
- An error for a misspelt or unknown name, such as `vidoe("x")`, names the line the name is on. Before, it named the line of an earlier clip, or no line. A loop that never ends names its line when the script has one loop, a mistake in the grammar reads `line 2: SyntaxError: …` like every other error, and two misspelt methods on one line name the one that failed instead of saying "not a callable function".
- A tip shown for a word in the code goes away when the pointer moves off the text, onto the empty space after a line, below the last line or up to the pane's header. Before, it stayed up and covered the next line.
- Marks set with `m` and a letter are cleared when another script is opened. Before, a mark from one project was still drawn on the next project's ruler.
- The New project dialog says "Type a name for the project" until the project has a name. Before, it said it would create `edit.js` straight in the chosen folder, which it never does.
- Asking to quit again while "An export is running. Quit and stop it?" is still open no longer puts a second copy of the question behind the first.
- When an export ends while the script has an error, the status bar says "exported …", or why the export failed, in front of the error, and shows the export's progress there too. Before, it showed only the error, so nothing told you the export had finished.
- `:history clear` asks "Remove all saved versions?" and removes them only on Remove, as the clear link in the History list does. Before, the command removed every version at once without a question.
- The `:help` panel fits the window: long lines wrap, and in a window too short for all of it the panel scrolls. Before, it was wider than the window, so the first and last words of every line were cut off.
- The timeline bar leaves out the buttons that do not fit when the left pane is narrow: first the timecode, then undo, redo, delete and the microphone, then the speed, T, ✎ and +. Before, in a small window or with the code pane dragged wide, the buttons were drawn on top of each other and the timecode ran over the code.
- A JPEG used with `image` now shows in the preview and as its timeline thumbnail. Before, most JPEGs drew nothing there, though they did appear in exports.
- A colour table (`.cube`) file edited or exported again while Origami is open now shows its new colours at once, in the preview and in exports. Before, a clip kept the table it was first drawn with until Origami was restarted.
- Exporting while the script has an error, from the Export dialog or with `:export`, first shows the error and asks whether to export the last version that worked. Before, it exported that older version without a word.
- Quitting during an export, and choosing Quit when asked, removes the hidden half-written file next to the output and the export's temporary folder before Origami closes. Before, both were often left behind, the file as large as the export had got. Stopping `origami render` with ctrl-C in a terminal now cleans up the same way; before, it left both too.
- `origami render --dry-run` and `:export --dry-run` no longer leave an empty folder in the Mac's temporary folder each time. Before, every dry run left one, and hundreds piled up. A folder is kept only when the printed command reads pictures of text or shapes from it, and the editor page now says where it is and that it is yours to delete.
- A sound, or a film's sound, that starts after a silence at the beginning of the timeline is exported with that silence, so the export's sound starts at 0 and lasts as long as its picture, and playing in the editor hears it at its place. Before, the export's sound track began where the first sound did, which some players and editors show out of step, and the editor played the sound straight away instead of at its time.
- Timeline thumbnails show a picture all along a film that has few keyframes, such as a screen recording or a clip encoded with one keyframe at its start. Before, every thumbnail after the film's last keyframe was blank, so such a clip showed only its first.
- Saving no longer hangs if another program swaps the script for a pipe at the very moment of the save; the save fails with its reason and your changes stay marked as unsaved.

### Nov 22

- The New project dialog treats a link named `edit.js` in the chosen folder, even one leading nowhere, as a script that is already there, and never writes through it. Before, a link to a missing file made Origami create that file, wherever the link pointed, with the starter script. Recording a voice take likewise skips a take number whose file is a link, so a failed recording never deletes it.
- A script whose folder or file name holds a line break is left out of the recent projects list that Origami keeps between launches. Before, it came back as made-up entries, one of which could lead to a different script elsewhere on the Mac.
- A still image whose name holds a frame number pattern, such as `image("a%d.png")` or a folder called `100%d`, now shows that very file, at its own size, in the preview, the timeline and the export. Before, ffmpeg read it as a numbered sequence and showed a neighbour such as `a1.png`, or nothing. Names with a lone `%`, such as `50%.png`, and films and GIFs read as before.
- Exporting a badly damaged video no longer hangs. Its stream of decoding errors filled a pipe that Origami only read once ffmpeg had finished, so the export waited 30 seconds and failed, or never ended; it now ends at once with ffmpeg's own error, and a damaged video that ffmpeg can still read exports.
- The pictures an export writes for its text and shapes go into a new folder that only you can open, and are deleted when the export ends, also when ffmpeg cannot start, when its messages are not plain text, or when Origami is force quit. Before, those cases left them behind, up to a gigabyte for each very large layer.
- A text holding a control character, such as `text("ding\u0007")` or an escape character pasted from a terminal, is drawn without it: the character takes no room and draws nothing. Before, drawing such a text stopped with an internal error (a division by zero) instead of showing the frame.
- A hand-written clip object that marks a sound as something to draw now gives the error "is a sound, which has no picture to draw" on its line. Before, a sound with a huge width made the preview and exports work on a picture billions of pixels wide, which never finished.
- Starting Origami or the `origami` command-line tool with a file path that is not valid text, which a shell can pass, no longer crashes it at once; `origami` says the script is missing.
- The preview is drawn at most 8192 pixels on its long side, also with `preview: "full"`. A timeline larger than 8K, up to the 16384 allowed, is previewed at half size or less, so ten full-size layers on a 16384×16384 timeline take roughly a quarter of the memory (about 2.6 GB instead of about 10 GB, worked out from smaller sizes), where before opening such a project could make macOS close Origami. Timelines up to 8192 pixels wide and tall, which includes 4K and 8K, preview exactly as before, and exports are unchanged.
- Dragging an end of a very short sound or film in the timeline, such as a 20 ms click, trims it to the shortest length, 0.04 seconds. Before, it closed Origami.
- A hand-written clip object that ends before it starts now gives the error "has a time or speed out of range" on its line. Before, Origami could close as soon as it showed that clip in the code or the Motion tab.
- Opening a project shows its code at once, and while it takes longer than a tenth of a second to load, the picture says "loading edit.js" and then "drawing the first frame". Before, the code appeared a moment after the window, with nothing to say the project was still loading. Opening another project no longer leaves the previous project's clips on the timeline while the new one loads, where editing one would have written that change into the new script.
- Opening Origami with a script (`origami-app edit.js`) works out the script while the window is still being made, so the timeline is usually there in the window's first frame, and the first picture starts drawing as soon as the window is laid out instead of a moment later. On a busy test Mac the timeline showed about 80 ms sooner and the first picture about 30 to 70 ms sooner. The timeline and picture are unchanged.
- While a project loads, the timeline's thumbnails and waveforms wait until its first picture is shown, so they no longer slow that picture down. On a busy test Mac the first picture of a 1080p project with 12 cuts and picture effects appeared in about 0.93 s instead of 1.15 s at best. The thumbnails and waveforms follow right after and look the same.
- The window appears about a tenth sooner: the menu bar is now filled in just after the window is first drawn instead of before. On a busy test Mac the launch screen came up in about 107 ms instead of 118 ms at best. The menus and their keys are the same.
- A script that is there but cannot be read, such as one saved in an older text encoding instead of UTF-8, still opens with its error and an empty editor, but saving no longer writes that empty editor (or anything typed into it) over the script; the code stays marked as unsaved changes. Before, ⌘S erased the script.
- A matte made from a merged group, or from a clip that has its own matte, now cuts with that whole clip, with its scale, place, effects and own matte. Before, it used the clips inside the group as if the group were not there, or only the innermost matte.
- Groups and mattes nest up to 16 deep; one more gives the error "is inside itself or inside more than 16 groups and mattes" on its line. Before, about 150 nested groups took about 1.2 GB and 3 seconds for one 1080p frame, and a hand-written clip object could put a group inside itself, which closed Origami as soon as the frame was drawn. 16 nested groups take about 130 MB.
- A save that cannot be written, such as onto a full disk or a read-only drive, now keeps your changes on screen as unsaved and says why in the status bar, and Save when Origami asks about unsaved changes then stays open instead of closing and losing them. Before, the failure was silent. Saves are also written to a hidden file beside the script and moved into place, so a save cut short leaves the last saved script whole instead of half written; the file keeps its permissions and Finder tags. The same goes for `origami.lock` and Origami's own files.
- Origami › Check for Updates… says "Could not check for updates" when it cannot reach origami.video or gets an answer it cannot trust, instead of saying you have the newest version. When a version of Origami is no longer supported, it says so in an alert each time it opens, with Download and Later; it keeps working either way.
- A clip method Origami does not know, such as a misspelt `.tirm(0, 1)` or one from a newer version, is named in the error: "line 3: tirm is not a clip method: check the spelling, or the script may need a newer Origami". Before, it said "TypeError: not a callable function". A line with more than one unknown call still shows the old message.
- `:export name.mp4` onto a file that already exists asks Replace, Keep Both or Cancel, as the Export dialog does, instead of writing over it without a word, which could replace footage another script uses. `:export --dry-run` asks the same before replacing an `export.sh` in the project folder.
- Saving can no longer leave your script empty or cut short. Before, a save on a nearly full disk emptied the file first and then ran out of room, and Origami said nothing. Now the new text is written to a separate file and swapped in only once it is whole; if the save fails, the status bar says why until a save goes through, the code stays on screen marked unsaved, and Save on the unsaved-changes question waits instead of closing. A read-only script, which also failed silently, now says so the same way.
- `origami frame` refuses to write its still over a picture or video the script reads, as exports already did. Before, `origami frame edit.js 1 photo.png` replaced `photo.png` without asking.
- A huge `blur`, such as `.blur(1e9)` or a function of time that returns one, no longer freezes the preview and exports. A number over 16384 is lowered to 16384 and the status bar says so, and any blur wider than its picture is drawn as wide as the picture, which looks the same. Before, such a blur kept every core busy for hours and the frame never showed; it now takes well under a second.
- Picture effects (`roughen`, `blur`, `lens`, `displace`, `noise`, `fractal`, `levels`) now show on text animated letter by letter with `each` or `shown`. Before, they were silently left out of the preview and the export.
- A script Origami cannot read as text, such as one saved in another editor with a non-UTF-8 accent, one over 16 MB or a folder named `.js`, is no longer opened as an empty page. Before, the editor showed nothing and the next save replaced the whole file with what you had typed. Now Origami says why it was not opened and leaves the file as it was.
- Code you have typed but not saved now survives a force quit, a frozen Mac or a power cut. Before, it was kept only when Origami crashed or quit normally. Now a copy is kept in Origami's own folder each time the code changes, and the next open brings it back with the keep mine / use disk bar; the copy goes away once the code is saved or the changes are discarded.
- When another program changes the script while you have unsaved changes, its text is now kept in History as a version named "changed on disk". Before, choosing keep mine wrote over it with no way back.
- Opening a script that has a mistake or points to missing footage no longer keeps showing the script you had open before, and Export no longer writes that other script's film under the new one's name. The picture and timeline stay empty until the script works.
- `for` on a `stack`, a `cat` or a merged group now cuts the clips inside at its end, sound included, and the video ends there too. Before, a clip inside with its own length, such as a trimmed video, kept playing: a merged group went black but its sound and the timeline ran on, and a plain stack ignored the `for`. `loop` now repeats a whole stack, cat or merged group; before, it did nothing on them. `trim` on a stack or cat and `speed` on a merged group, which did nothing, now stop the script with an error on their line that says what to write instead.
- A video used as a matte is no longer heard, in the preview or the export. Before, its sound was mixed in unless you added `.mute()`.
- `at` and `shift` on a matte now move it from the start of its clip, so a matte can come in later than its clip. Before, they were ignored and the matte always started with its clip.
- Effect values outside what the effect can draw are brought inside its range, and the status bar says so, naming the line: `lens` past 170 either way, keys and functions of time included, `levels` with white at or below black, `noise` outside 0 to 1, a `fractal`, `roughen` or `displace` size or scale under 1, and a negative `roughen` border or sharpness. Before, they were used as written: `lens(180)`, a `roughen` or `displace` size of 0 and a `fractal` scale of 0 made the clip vanish or turn black, a negative sharpness hollowed a shape into a ragged frame, and `levels(0.6, 0.4)` was a hard cut with no warning.
- Autocomplete and the help shown when you hover a call now know `path`, `merge`, `matte`, `blend`, `fps`, `duotone` and the seven picture effects (`lens`, `blur`, `levels`, `noise`, `fractal`, `roughen`, `displace`), each with a one-line description. `merge` is offered only after a `stack` or `cat`, and the picture methods are not offered on a `sound`.
- Clicking `displace({ amount: 50 })` opens an amount slider from 0 to 100 pixels. Before, it ran from 0 to 1, like a colour amount, so any drag rewrote the amount to 1 or less, and the editor underlined amounts over 1 as out of range.
- Dragging a `path` in the preview now moves it, writing `.pos(x, y)` into the script as for other shapes, and its position can be changed in the Motion tab. Before, a path could be selected but a drag left the script as it was.
- A timeline that shows more videos at once than Origami kept decoders for (four on a Mac with 8 GB of memory, six on larger ones), such as a wall of 12 picture-in-picture videos, now keeps one decoder for each video on screen instead of starting ffmpeg again for every layer of every frame. A 4-second 1080p export with 12 videos, 14 titles and 14 moving shapes used about 179 seconds of processor time and now about 17. The pictures are unchanged.
- In footage with B-frames, which most cameras and phones record, Origami looks up where each clip's first frame is with a short ffmpeg run. An export now does this for every clip at once, on all cores, before it draws the first frame, and the preview does it in the background after each change, instead of one clip at a time as playback reaches it. Playing across a cut no longer pauses for it, and a montage of 300 cuts of 0.2 seconds waited about 30 seconds in total for these lookups during its export and now about 4 seconds at its start (measured while the Mac was busy with other work). The pictures are unchanged.
- While playing forwards and exporting, each video's next frame is now read from ffmpeg while the current frame is drawn, instead of only when it is needed. Measured while the Mac was otherwise fairly quiet, a 4-second 1080p export with 12 cuts, a picture-in-picture video, roughened images and a matte finishes about 15 to 20 percent sooner, and one with 13 videos on screen about 15 percent sooner; a montage of 300 short 640×360 cuts is unchanged. Each video being played holds one frame more, about 20 MB more at most in these exports. The pictures are unchanged.
- When Origami is force-quit or crashes during an export, the folder of temporary layer pictures that export was using is now removed along with the half-written file, instead of staying in the Mac's temporary folder. An export of 20 titles and 20 boxes over 720p video left 8.5 MB behind each time.
- A colour table (`.cube`) file used by `lut` or `look` is kept in memory once per version of the file only for the 32 most recently read, instead of every version and every file read since Origami opened. Each version of a 65-point table takes 3.3 MB, so re-exporting one from a grading app 50 times while Origami was open kept about 160 MB of old tables.
- Origami keeps at most the 16 fonts used last read in memory, instead of every font any title used since it opened. A font can take a lot of memory once read (Arial Unicode, which draws letters a title's own font lacks, such as Chinese or Japanese, about 360 MB; most fonts 1 to 15 MB), and playing 120 titles each in a different font held about 1.36 GB until Origami quit; now it stayed under about 520 MB.
- The timeline's clip thumbnails no longer pile up for as long as Origami is open. Every thumbnail ever shown, at every zoom level and trim, stayed in memory twice (about 70 KB in the app and 70 KB of graphics memory each, so 3,000 thumbnails come to about 400 MB). Now thumbnails not shown since the timeline last gathered 500 are let go, from both; a thumbnail on screen stays, and a sound's waveform is kept.
- Opening a script whose media Origami has not read before (no `origami.lock` yet, or new or changed files) reads each file once. Before, every clip after the first that used the same file read it again, one at a time: a montage of 300 cuts from 5 new files took about 14 seconds to open and now about 0.2 seconds, and 300 files each used twice took about 14 seconds and now about 3. The timeline and `origami.lock` are unchanged.
- A long script with more than about 10,000 names defined at its top level, as generated scripts can have, now evaluates instead of stopping with `RuntimeLimitError: reached the maximum stack size on this execution`, which named no line. A 50,000-line script with 10,000 named clips evaluates in about 4.6 seconds. Scripts that make their clips in a loop or an array, rather than naming each one, evaluate faster: 12,000 titles in about 1.4 seconds.

### Nov 21

- Picture effects (`roughen`, `blur`, `lens`, `displace`, `noise`, `fractal` and `levels`) on an image, shape or text, and on a video stepped to a lower rate with `fps`, are worked out once and kept while the picture and the effect's settings stay the same, instead of again on every frame. A 1080p export of 2 seconds with a roughened 1400×900 image in multiply over video took about 2.2 s and now takes about 0.7 s, and its memory peaked at about 58 MB and now at about 44 MB, because an image or shape whose effect never changes keeps only the finished picture. Playing such a timeline saves about 30 ms a frame for each roughened full-size image. A playing video's effect is still worked out for each new frame, so it holds no extra memory. The pictures are unchanged.
- `blur` on a picture that changes every frame, such as a video, is worked out on every core and in place: 2 seconds of blurred 1080p video export in about 1.8 s instead of 3.1 s, and a blurred 1080p frame takes about 30 MB less memory. The pictures are unchanged.
- An effect on a clip drawn less than a pixel wide, such as a video scaled down to almost nothing, no longer stops Origami; the clip is simply not drawn, as without the effect.
- `roughen` measures how far each pixel is from the picture's edge about four times faster. A roughened 1400×900 image is ready about 15 ms sooner the first time it shows, and 2 seconds of a roughened 1344×756 video over another export in about 1.3 s instead of 1.5 s. The pictures are unchanged.
- A `path` whose points move only for part of its clip no longer works out its outline again for every later frame on every frame drawn. A 60-second 320×180 export of a 16-point curved path animated over its first 2 seconds took about 5.5 s and now takes about 1.1 s. The pictures are unchanged.
- Groups, mattes and layers that are blended in multiply, moved, turned or stepped are drawn with less work: the clear pixels of a layer are skipped, a layer that sits on whole pixels reads one pixel of its picture instead of four, and a matte's mix and a group's colour pass use every core. A 2-second 1080p export of a group over video took about 0.95 s and now about 0.7 s, and of a video behind an alpha matte about 1.6 s and now about 1.2 s; an image in multiply over video uses about a quarter less processor time. With the changes above, a 4-second 1080p export with 12 cuts, a picture-in-picture video, three roughened images in multiply, two roughened moving shapes, a group and a matte took about 11.4 s and now takes about 4.5 s, using less than half the processor time, at the same peak memory. The pictures are unchanged.

### Nov 20

- With the search bar open, clicking in the code now sends your typing to the code. Before, it kept going into the search box. Click the bar or press ⌘F to type in the search again.
- Origami is now open source under the GNU General Public License, version 3: anyone may use, change and share it, and whoever shares it or a changed version shares the source under the same licence. Before, it was under the Functional Source License, which did not allow competing commercial use for two years.
- Origami's own text, in the code, the timeline and every panel, is now set in Paper Mono, which is built into the app. These docs use it too. Text in your videos is unchanged.
- While scrubbing, a `.LRF` proxy beside a clip is only used when it is a plain file. One that is something else, such as a named pipe, is skipped in favour of the clip itself; before, it could stall the preview for 20 seconds at a time.
- Reading media takes far less memory for huge pictures: a 1 MB, 16000×16000 PNG made each read of it take about 1 GB, and now takes about 6 MB, because ffprobe no longer decodes the picture just to learn its size. A project opened for the first time reads at most 8 new media files at once instead of 32. The sizes, lengths and kinds Origami learns from each file are unchanged.
- Playlist files are refused: `video`, `sound` or `image` on an HLS playlist (a `.m3u8` or `.m3u` file, or any file starting with `#EXTM3U`) or an ffmpeg concat list (a file starting with `ffconcat`) now gives the error "playlist files are not supported: use a video or sound file" on its line at once, even when `origami.lock` lists the file. The preview, thumbnails, waveforms and exports never hand such a file to ffmpeg either, and a `.LRF` proxy that is a playlist is skipped in favour of the clip itself. Before, a playlist that keeps waiting for its next part could stall them for 20 seconds or more each time.
- The timeline's thumbnails fill in about twice as fast for footage that has a small `.LRF` copy beside it, as DJI and GoPro cameras record: they are read from that copy, so they look the same at the same size. A copy that cannot be read, or that ends before the clip does, is skipped for the clip itself.
- Pressing play no longer freezes the window while Origami reads the media it is about to play. The play button changes at once and the playhead waits where it is until the sound is ready, so a file that takes long to read (up to 20 seconds for one that never answers) no longer stops typing, scrolling or pausing meanwhile.
- After a click in the code, backspace always removes the letter behind the caret. Before, the first backspace left a hidden one-letter selection, so the second one removed the letter in front; a pointer that slipped a pixel during the click did the same on the first. Dragging more than 3 pixels still selects.
- The caret in the search field sits right after the last letter instead of a gap away, and in front of the greyed "Search…" hint while the field is empty.
- A media file that never ends, such as a live HLS playlist (`.m3u8`) that keeps waiting for its next part, no longer freezes the preview, an export or the timeline's thumbnails until Origami restarts. An ffmpeg or ffprobe that sends nothing for 20 seconds is now stopped: the clip shows black where it could not be read, and a file the script is still reading gives an error on its line.
- A sound's waveform in the timeline covers at most the first day of the file, and is worked out without keeping the whole decoded sound in memory. Before, a tiny sound file with one sample a second could take gigabytes of Origami's memory.
- Exports use less memory: a 1080p export keeps only the video frames its layers need, so its peak memory fell from about 105 MB to about 65 MB (about 88 to 52 MB with two or three video layers). A 4K export with three or more overlapping video layers, one of them slowed down, no longer restarts a decoder for every repeated frame, so it finishes several times sooner (about 6 s instead of 35 to 60 s for a 4-second example).
- Stepping backwards one frame at a time no longer pauses about every second: while you step through the frames Origami has kept, it reads the ones before them in the background. Stepping back toward a cut also reads the end of the clip before it, so crossing the cut no longer waits about half a second. Stepping back 120 frames of 4K footage across two cuts took about 3.6 s with two to three pauses of about 0.3 s, and now takes about 1.3 s. Stepping back three frames at a time pauses about a third as long. Going back over the same few seconds again can find a few more frames to read, because the frames read ahead take up to a quarter of the preview's frame memory.
- A long timeline cut from a few media files uses less processor time while Origami sits idle: it checks each file for changes once per screen refresh instead of once per clip (with 451 clips from 34 files, about 0.05 ms of every 16 ms instead of 0.4 ms).

### Nov 19

- A timeline with more lanes than fit, such as 55 stacked layers, keeps every lane at least half its usual height instead of squeezing them into a few pixels each. Scrolling up or down then moves through the lanes, and cmd+scroll zooms; when every lane fits, scrolling zooms as before.
- **Scripts run in a helper process.** A script that runs for more than 30 seconds, or uses more than 2 GB of memory, is stopped and its error shows like any other, even when one call never returns (a runaway regular expression, a huge array). Before, such a script kept running in the background and could take all of the Mac's memory and close Origami. While a script is still reading new media files it gets more time, up to 5 minutes.
- A script whose timeline is over 16 MB as text (tens of thousands of clips, or one huge value), or that animates more than 1,048,576 values, is stopped with an error. Before, reading such a timeline back could take several gigabytes of Origami's own memory.
- A captions file with more than 262,144 lines is refused with an error naming the line. Before, a file of many blank lines kept the script busy until it was stopped after 30 seconds.
- Long captions files load several times faster: a day-long .srt with 30,000 captions took about 20 seconds on every run, and now takes about 6.
- Reading back a script's timeline takes far less of Origami's memory: a timeline with millions of animated numbers and one bad clip took about 900 MB, and now takes under 50 MB. The bad clip's error now always names its own line, even when a clip before it changes over time.
- If Origami is updated or moved while it is open, a script that needs a fresh helper now says "Origami was updated: restart it to run scripts" instead of running with the new version's helper.
- The update notice only shows a version made of numbers and dots, and only links to a plain address on origami.video.
- A force-quit or crash during an export no longer leaves a hidden half-written file beside the destination.
- A project can no longer run the Mac out of memory by naming one font or colour table through many spellings of its path (`./a.ttf`, `././a.ttf`, …): each file is read and kept once.
- An export at a size larger than the timeline that would draw a clip over 16384 pixels on a side, such as very large text on a small timeline exported at 4K, now stops with an error naming the clip's line instead of crashing Origami.
- Recovered unsaved code and remembered export choices are only offered for the exact script they were kept for, never for another script that happens to share their file name in Origami's folder. Export choices and unsaved code kept by earlier builds are not offered again.
- Saved versions written while quitting are flushed to disk before Origami exits.
- The code pane shows at most 500 warnings at a time, plus the script's error. A line of tens of thousands of brackets no longer freezes Origami for seconds on opening and after every keystroke, and the Graph tab no longer freezes on a script of about a thousand clips that follow one another. Autocomplete, search and folding also stay quick on scripts with tens of thousands of names, matches or brackets.
- A line of hundreds of thousands of characters no longer slows the code pane or fills the Mac's memory: its error squiggle, search highlights and colours are only drawn for the part on screen.
